## 卡片

### A1 narrations.ts 唯一真相源 · 维度：领域-认知

**症状:** 稿子切了 36 段、页面写了 41 步、音频合成了 38 个 mp3。`?auto=1` 录到第三章，口播在讲 Cursor，画面停在 Copilot——对不上嘴，而且没人知道三个数字哪个是对的。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 章节组件里写 `totalSteps = 9`，音频流水线从 outline 数 step——同一个数字存两处，改一处忘一处 | 每章一个 `narrations: string[]`：长度即 step 数，元素即音频文本；注册表里连 totalSteps 字段都不存在 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 别写校验脚本对账——改设计，让这个数字只有一个存放处，其它地方连存它的字段都没有。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> **真相源**：每个章节的 `src/chapters/<NN>-<id>/narrations.ts` 是 step 数 + 口播文本的**唯一来源**。`outline.md` 不再参与音频合成，章节代码也不再手写 `totalSteps`。这一改根除了"网页 step 和音频文件数对不上"这个老问题。

「不再」「老问题」——这是修过的伤，不是预防性设计。注册表注释补了机理：its length is the chapter's step count — there is no totalSteps to maintain separately。

**机制说明:** 同一个数本来抄了五份，现在只许存一份，其它地方全改成引用。它不是靠检查防住跑偏的——是想跑都没地方跑：你想写一个不一样的 step 数？没有字段给你写。
**解法层次:** 表征解法
**可迁移性:** 高
**什么时候用:** 任何「同一个数字 / 文本被多个下游消费」的流水线——配置、schema、多语言文案，先问「真相能不能只存一份」。
**什么时候太重:** 两个消费方天然异构（比如一个要中文一个要英文），强行单源会让那个文件变成大杂烩——这时要的是「单源＋派生」，不是「单文件」。
**反例:** 「写个 CI 脚本检查两边一致」不是这招——那是接受了多副本再雇人对账；这招是消灭副本。
**在哪几个 skill 里见过:** web-video-presentation；同构于编程里的 single source of truth / normalization。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| step 数这类被 5 方消费的硬数字 | 管用 | 漂移即灾难，单源收益最大 |
| outline 里的 step 预估 | 得让一步 | skill 自己说了「outline 的 step 数是初始预估」，实现后回头同步——计划层允许暂时失真 |
| 一次性脚本里的局部常量 | 没必要 | 没有第二个消费方，单源是空转 |

**一起读:**
- A9 删掉 minHoldMs：动画 ≤ 口播（下游接管：真相源定了 step 的「数」，A9 管每个 step 的「长」）
- A2 outline 不写动画（对照：A1 是「必须钉死的」，A2 是「必须留白的」——同一张计划表的两面）

### A2 outline 不写动画：计划留白防翻译机 · 维度：领域-认知

**症状:** 规划阶段把每步动画写死（「此处 blur clear」「此处弹簧」），章节实现照单翻译——全片 38 步清一色 fade-in 变奏，观众十秒看出是同一个模板的 N 次复制。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| outline：「step 3 (~6s) — 金句淡入＋光晕呼吸，800ms ease-out」 | outline：「step 3 (~6s) — 反差句『有人救了结尾』金句独占」——动画、手段、时长一个不写 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 计划只锁改起来贵的决策（内容、节奏、信息密度），把需要看着内容才能做对的决策（视觉）推迟到实现现场。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> **outline 不写动画的理由**：写死动画 = chapter agent 退化为翻译机；留白让 chapter agent 在每步开工时按 CHAPTER-CRAFT.md 的"内容驱动决策树"自由设计，才有真正的视频感。

OUTLINE-FORMAT.md 还把禁令做成了表：动画类型、CSS 手段、时长数值、错峰量，全在「不要写」列。

**机制说明:** 「计划越细越好」在这里是反的：上游写得越满，下游就越没有发挥的余地，最后只能照抄。留白不是偷懒，是故意把视觉决策留给看得见内容的那个环节。怕放飞？完工自检里有一条「不同 step 主导动作不一样」兜着。
**解法层次:** 表征解法
**可迁移性:** 高
**什么时候用:** 任何「规划 agent ＋ 执行 agent」的两段式流水线：规划层只写 what 和 why，把 how 留给手里握着完整上下文的执行层。
**什么时候太重:** 执行层不可靠或没有质量门禁时，留白等于放飞——先有完工自检这类兜底，才配得上留白。
**反例:** 「需求写得模糊一点让 AI 自由发挥」不是这招——这招的留白是有边界的：内容和节奏照样钉死，只留视觉一个维度的白。
**在哪几个 skill 里见过:** web-video-presentation；同思路见于「给结构不给措辞」的写作类 skill。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 视觉 / 文风这类强上下文决策 | 管用 | 只有看着具体内容才能做对，提前定必错 |
| 安全红线、命名规范 | 用不上 | 这类决策不依赖现场上下文，就该提前钉死 |
| 执行层是便宜小模型 | 也许碍事 | 判断力不够，留白产出的是随机而不是设计 |

**一起读:**
- A1 narrations.ts 唯一真相源（对照：同一张表上「必须写」和「不要写」两列的设计逻辑）
- A8 token 兜底的并行隔离（搭配用：留白的自由靠 token 和自检兜底才不跑偏）

### A3 信息保留度 ≥ 60% 硬下限 · 维度：行为

**症状:** 2000 字的测评文章被「精炼」成 600 字口播稿：五个工具砍成三个，唯一的反方观点（「但 Copilot 在长文上反而最稳」）整段消失——用户拿到的是摘要朗读，不是他那篇文章的视频。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 「帮你提炼了核心要点，更适合视频节奏」——删了 70%，听起来还很专业 | `len(script) ÷ len(article) ≥ 0.6` 机器可验；原文太长时上报：「按 60% 留存最少需要 ~Y 分钟，要么拉长要么拆集」 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 给「悄悄降质」上一个能用 `wc -m` 验的硬下限，并把「内容装不下」从 agent 的私下取舍升级成必须上报用户的决策。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> **如果原文确实太长**（比如 5000+ 字 article 做 3 分钟视频）→ 不要靠压缩硬塞，**告诉用户**……**不要**自作主张缩到 30% 然后假装做完了。

配套的禁删清单点名了 AI 最爱删的东西：「反方观点 / 限制条件 / 例外情况（最容易被 AI 一刀切掉）」。

**机制说明:** 三样东西各管一段：数字下限管「最多删多少」，点名清单管「哪些绝对不能删」，上报规则管「实在装不下怎么办」。AI 想悄悄把稿子删薄？三条退路全被堵上了。
**解法层次:** 流程解法
**可迁移性:** 高
**什么时候用:** 任何转写 / 改写 / 翻译类任务——凡是「换说法」容易滑成「删内容」的地方，都值得立一个机器可验的保底比例。
**什么时候太重:** 任务本来就是摘要（用户要的就是三句话总结）——这时 60% 下限直接顶撞任务目标。
**反例:** 「尽量保留原文信息」不是这招——没有数字、没有验法的要求等于没提。
**在哪几个 skill 里见过:** web-video-presentation；同型于翻译 skill 的「术语表逐项对照」。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 文章转口播 / 转课程脚本 | 管用 | 「换说法不删货」正是任务定义 |
| 原文水分大（营销稿、套话多） | 可以松点 | skill 自己也豁免了「套话开场 / 重复总结」；死抠 60% 会保留垃圾 |
| 摘要任务 | 用不上 | 任务目标就是压缩 |

**一起读:**
- A4 去 AI 味三层自检（搭配用：A3 管内容不丢，A4 管腔调不油——同一站的两道闸）
- A12 双源原则＋信息池（下游接管：口播装不下的细节，A12 让它们从画面回来）

### A4 去 AI 味三层自检：最后一层是张嘴念 · 维度：品味

**症状:** 稿子短句化、第二人称、口语词全做到位，开头仍是「我知道你最近肯定很纠结选哪个工具」——念出来一耳朵推销味。形式清单全过，腔调全错。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 自检 = 过一遍 8 条形式原则，全勾，交稿 | 形式 8 条之后还有两层：扫五类腔调指纹（假共情 / 假深刻 / 自我标榜 / 万能模板 / 排比），然后挑 3 段**真的张嘴念**，说不出口的句子就是 AI 味 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 品味检查不能全清单化——清单查得了形式，查不了腔调；最后一道闸必须换通道（从看换成念）。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> 随便挑 3 段念出来 —— 不要在心里默读，**真的张嘴念**。
>
> - 念到哪句你觉得"这话我说不出口" → 那句是 AI 味
> - 念到哪句你想跳过 → 那段是排比 / 自我标榜
> - 念到哪句你想笑出声（不是因为内容好笑，是因为油腻）→ 那句是假共情

五类指纹清单本身也值得偷：它不是「写自然点」，是给每类配了典型句式黑名单＋改法。

**机制说明:** 三步越来越难自动化：第一步机器能查，数句长、搜违禁词就行；第二步拿着指纹清单扫；第三步只能靠人张嘴。为什么最后非得念？因为口播稿最终是给耳朵听的，不是给眼睛看的——验收就该用耳朵验。
**解法层次:** 流程解法
**可迁移性:** 高
**什么时候用:** 产物的消费通道和生产通道不同时（写出来的稿子要被念、做出来的页面要被录屏、写出来的代码要被 review）——验收就该在消费通道上做。
**什么时候太重:** 产物不过人耳（内部文档、配置说明）——念出来测试空转。
**反例:** 「写完再通读一遍」不是这招——默读走的还是生产通道；要点是换通道。
**在哪几个 skill 里见过:** web-video-presentation；同思路如「设计稿必须在真机上看一遍」。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 口播 / 演讲 / 对话体文案 | 管用 | 耳朵是最终法官，提前用耳朵验 |
| 知乎体长文 | 得让一步 | 书面语合法，五类指纹仍适用但「念出来」标准要放宽 |
| API 文档 | 用不上 | 没人念它 |

**一起读:**
- A3 信息保留度 ≥ 60% 硬下限（搭配用：同一站先保内容再修腔调，顺序不能反）
- A10 自检协议：先修复再汇报（前置：三层自检的结论怎么处理，A10 管）

### A5 1 项 = 1 step：逐个揭示 · 维度：行为

**症状:** 口播说「这五个工具各有各的脾气」，画面一个 step 把五张卡 stagger 全亮。你刚讲到第二个，观众已经把第五个读完了——后面三十秒他在等你，不是在听你。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| step 7：五个工具卡 0.1s 错峰依次入场，齐活 | step 7~11：每个工具独占一步；讲到 Cursor 时，Claude Code 灰化保留作上下文 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 画面节奏的最小单位必须等于口播节奏的最小单位——讲者会逐个念的清单，画面就必须逐个亮。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> 当口播在说"第一是 X、第二是 Y、第三是 Z"这种**清单 / 列表**时，**严禁**一个 step 把 X / Y / Z 全部 stagger 上来。
>
> - 一项 = 一个 step
> - X 只在它自己的 step 里独自亮起
> - 讲到 Y 时，X 灰化保留作上下文 + Y 亮起

判断标准也给了：「讲者会一个一个念出来吗？会 → 必须逐个揭示。」

**机制说明:** 列表错峰全亮是前端的审美本能，显得精致——但那是给「自己逛网页的人」准备的。视频观众是跟着讲解走的，画面抢在嘴前面，人就跟丢了。灰化保留是这招最妙的部分：当前项亮着，讲过的变灰但还在，聚焦和上下文两头都占住了。
**解法层次:** 流程解法
**可迁移性:** 高
**什么时候用:** 一切「叙述驱动画面」的产物：演示文稿、教学动画、产品 walkthrough——画面揭示速度对齐叙述速度。
**什么时候太重:** 真正的「一览」场景（对比表格就是要全局看）——skill 也只管「讲者逐个念」的清单，不禁一览式画面。
**反例:** 「加长 stagger 间隔到 2 秒」不是这招——观众还是在第一个 step 里看完了全部；要点是揭示权交给点击，不是放慢动画。
**在哪几个 skill 里见过:** web-video-presentation；keynote 高手的「build 一次只加一件事」是同一招的人肉版。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 口播逐项展开的清单 | 管用 | 画面和嘴同步，注意力不抢跑 |
| 「先看全貌再逐个讲」的结构 | 看情况 | 可以先一步全亮再逐步聚焦——但那是设计出的全景步，不是偷懒 |
| 8 项以上的长清单 | 得让一步 | 8 个 step 太碎，先该问的是清单本身要不要砍 |

**一起读:**
- A12 双源原则＋信息池（搭配用：每个独占 step 的画面密度从信息池来）
- A9 删掉 minHoldMs：动画 ≤ 口播（可能冲突：拆出来的小 step 口播很短，动画得跟着短）

### A6 Checkpoint Plan：5 件事一次对齐 · 维度：需求

**症状:** agent 没停，从文章一路闷头做到 5 章全完工。用户看到成片第一句话：「这个黑底不是我想要的感觉。」——主题错了，38 步的视觉全部返工。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 写完稿子顺手选个主题开工；或者稿子问一次、outline 问一次、主题问一次、素材问一次、模式问一次——五次打断 | 一个硬节点一次对齐五件事；「主题必须明确才进入 Phase 2」；用户说「你帮我选」→ 代选＋公示理由＋留反悔窗口 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 把所有「错了会作废下游产物」的决策收进同一个检查点，一次对齐；对「你帮我定」给出明确接法，不让授权变成放飞。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> - **主题必须明确**才进入 Phase 2。用户说"主题你帮我选" → 取你推荐的第 1 个，**告诉用户你选了什么、为什么**，给反悔机会
> - 模式选定 → 进 Phase 2

预备作业也是机制的一半：「读所有 `themes/*/theme.json`……**不要硬编码清单**」——推荐基于当前包里真实存在的主题，清单永不过时。

**机制说明:** 这个检查点的位置是算过账的：它刚好卡在「该定的事都能定了」和「再往后每错一步都要乘以章节数」之间。五件事合并成一停也有来历——旧版是两个检查点，后来合成了一个，SCRIPT-STYLE 里还留着「流程变化提醒」。打断用户的次数，本身也是成本。
**解法层次:** 流程解法
**可迁移性:** 高
**什么时候用:** 流水线里存在「错了会作废 N 个下游产物」的决策时——把它们全部前置到生产开始前的同一个节点。
**什么时候太重:** 任务总成本本来就低（一页 landing page）——对齐仪式比返工还贵。
**反例:** 「做完给用户看一眼」不是这招——验收在下游，这招的要点是把确认提到成本曲线起飞之前。
**在哪几个 skill 里见过:** web-video-presentation；nuwa-skill 的双暂停点同构。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 多章批量生产前 | 管用 | 一次对齐挡住 N 倍返工 |
| 用户就在旁边实时反馈 | 可以简化 | 对齐本来就在持续发生，仪式可以轻 |
| 探索型任务（用户自己也不知道要什么） | 得让一步 | 五件事一次问到底问不出来，得用样品迭代代替对齐 |

**一起读:**
- A7 第 1 章风格锚点＋硬验收（下游接管：检查点对齐「纸面决策」，锚点验收「落地效果」）
- A3 信息保留度 ≥ 60% 硬下限（前置：稿子先自检合格，检查点上用户才有真东西可拍板）

### A7 第 1 章风格锚点＋硬验收 · 维度：编排

**症状:** 第 1 章没验收就并行开工第 2~5 章。指引在这个题材下的盲区（数据对比图的画法没写）让四个 subagent 各自发明了四种丑法——同一个坑修四遍。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 五章并行，问题 ×5 后才见人 | 第 1 章主线程一次做到「能直接验收」，用户点头才许做第 2 章；后续章节拿它当代码风格参考 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 批量之前先做一个完整样板过人审——指引的盲区一定会在第一次落地时暴露，让它暴露在成本最低的位置。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> - 它是 CHAPTER-CRAFT.md 这套指引在**当前主题 + 当前题材**下的第一次落地
> - 如果指引有盲区 / 主题颜色 / 字体 token 不够用，第 1 章一定会暴露——这时候有人类反馈就能修指引 / 调主题，**早改成本最低**
> - 后续章节（无论顺序 / 并行）都要参考第 1 章的代码模式

注意它同时强调「没有骨架版概念」——锚点必须是完整品，半成品验收不出气质问题。

**机制说明:** 第一章串行慢一点，换来后面 N-1 章放心跑——这是保险费。它和 A6 管的是同一本账的两段：A6 拦纸面上就能看出来的错，比如主题选错；这张卡拦的是只有做出真东西才看得见的错，比如颜色 token 不够用、指引没讲数据图怎么画。
**解法层次:** 流程解法
**可迁移性:** 高
**什么时候用:** 任何「同构子任务 × N」的批量生产：第一个必须串行做完整、过人审，剩下的才许批量。
**什么时候太重:** 子任务之间不同构（每章一个完全不同的媒介）——锚点的经验传不下去，白等一轮。
**反例:** 「先做个 MVP」不是这招——MVP 是减功能验证方向，锚点是全功能验证品质；锚点禁止减功能（没有骨架版）。
**在哪几个 skill 里见过:** web-video-presentation；本手册自己的生产流程（先写 anchor slice 再写全部页面）就是同一招。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 多章 / 多页 / 多图批量生产 | 管用 | 盲区修一次，N-1 次免疫 |
| 总共就两章 | 没必要 | 锚点仪式的开销接近收益 |
| 用户响应很慢的异步协作 | 得让一步 | 硬验收会让流水线停摆一整天——改成「锚点＋限时默认通过」 |

**一起读:**
- A8 token 兜底的并行隔离（下游接管：锚点立住后，并行才有资格开始）
- A6 Checkpoint Plan：5 件事一次对齐（前置：纸面对齐在先，落地验收在后）

### A8 token 兜底的并行隔离 · 维度：编排

**症状:** 三个 subagent 并行写章节，被要求「保持风格一致」。它们互相看不见：要么都去改共享的样式文件（合并冲突），要么各自发挥——一章蓝紫渐变、一章黑白、一章 emoji 满天飞。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 派工 prompt：「注意和其它章节保持视觉风格一致」 | 颜色字体锁死在主题 token；每章独立文件夹＋独立 CSS 前缀；不许动 chapters.ts；「风格不一致 = 人手写视频的呼吸感」 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 并行体不可能互相对齐——把「必须一致的」沉到共享只读层（token），把「可以不同的」明文重新定义为特性，把「会打架的」物理隔离。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> 1. 每个 subagent 看不到别的 subagent 产出，无法机械对齐
> 2. 章节代码物理分离（每章一个文件夹 / 自己的 CSS 前缀），不会互相破坏
> 3. 主题 token 兜底视觉统一（颜色 / 字体 / hero 数字 / 卡片 / 分割线性格 / 装饰），气质不会跑偏
> 4. **风格不一致 = 人手写视频的呼吸感**（多 voice / 多视角）

**机制说明:** 三层各管一件事：token 兜住下限，气质不跑偏；物理隔离保证安全，谁也改不到谁的文件；最后一步是定性——把剩下的差异从「毛病」改判成「特色」。这一步最容易被忽略，但它直接改了验收标准：从此用户不会再拿「这两章动画不一样」来报 bug。
**解法层次:** 表征解法
**可迁移性:** 高
**什么时候用:** 多 agent 并行产出同类产物时：先分层——哪些必须一致（沉到共享只读资源）、哪些必须隔离（物理分仓）、哪些差异可接受（明文定性）。
**什么时候太重:** 产物要求严格一致（法律条款的 N 个语言版本）——「呼吸感」的定性在这里是事故。
**反例:** 「把别人的产出发给每个 subagent 参考」不是这招——那是串行化的伪并行，又慢又对不齐。
**在哪几个 skill 里见过:** web-video-presentation；多章节写作类 skill 的「每章独立文件＋写作契约」同构。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 并行章节 / 并行插图 | 管用 | 下限有兜底，差异有定性 |
| 串行逐章模式 | 不用做 | 上一章就在上下文里，自然连贯——隔离仍有用但定性条款空转 |
| 品牌严格规范的商业交付 | 得让一步 | 「呼吸感」要先和客户对齐，否则就是风格不受控 |

**一起读:**
- A7 第 1 章风格锚点＋硬验收（前置：锚点给并行体提供公共参照物）
- A2 outline 不写动画（搭配用：留白给了各章自由，token 兜住自由的下限）

### A9 删掉 minHoldMs：动画 ≤ 口播 · 维度：领域-工程

**症状:** 某步做了 6 秒的粒子汇聚动画，口播只有 3 秒。`?auto=1` 录屏时音频一停立刻翻页——动画演到一半被切，成片里那一步像个事故。删除现场留在 extract 脚本的报错文案里，动机写在运行时注释里。（证据：实测）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| narration 支持 `{text, minHoldMs}`：动画不够长就让 step 多停一会 | narration 只能是 string；规则一条：动画时长 ≤ 口播时长，不够就「写更长口播 / 拆 step / 调动画速度」 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 两个时钟（音频、动画）必然漂移——删掉第二个时钟的调节旋钮，让单一时钟驱动一切，把矛盾推回内容层解决。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> The {text, minHoldMs} form was removed; if your animation is longer than the narration, write longer narration, split the step, or speed the animation up.

运行时注释给了动机：Audio playback is the sole driver of step duration — there is intentionally no "minimum hold" knob… This keeps Auto-mode behavior trivially predictable.

**机制说明:** 这是一次有据可查的减法：那个旋钮真存在过，后来被删了。它的问题不是不好用，是有了它之后，每一步停多久都得人脑算一遍「音频长还是动画长」。删掉之后规则就剩一句话：动画不许比口播长。查起来也简单——口播字数除以 4 就是秒数，心算就行。
**解法层次:** 表征解法
**可迁移性:** 低
**不可迁移原因:** 规则本体（动画 ≤ 口播）绑死在「音频驱动推进」这一架构上，换成手动点击的演示就没了意义；它背后的元招——「删旋钮换可预测性」——是高迁移的，但那是另一张还没第二个案例佐证的卡。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 音频自动推进的录屏流水线 | 管用 | 单时钟让 Auto 模式行为完全可预测 |
| 手动点击演示 | 用不上 | 推进时长由讲者手指决定，规则没有宿主 |
| 动画本身是主角（片头 logo 动画） | 得让一步 | skill 给的出路是「写更长口播」——给片头配几句旁白把时间撑出来 |

**一起读:**
- A1 narrations.ts 唯一真相源（前置：先有单一账本，才谈得上单一时钟）
- A5 1 项 = 1 step：逐个揭示（可能冲突：step 拆细后口播变短，动画预算跟着缩水）

### A10 自检协议：先修复再汇报 · 维度：行为

**症状:** agent 写完章节直接汇报「第 3 章做完了，请验收」。用户打开一看：纯文字三屏、一处硬编码颜色——这些它的自检清单本来就该抓住，但自检要么没做，要么做了没改。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 「实现完成 → 直接汇报给用户」；或者「自检发现 2 项 fail，特此汇报」 | 自检（优先独立 reviewer）→ 按 fail 项改完 → 汇报「做完了＋自检结论＋改了什么」；「直接拿原始结论汇报但不修复 = 违规」 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 把「自检 → 修复 → 汇报」定成不可跳步的顺序，并且自检尽量交给没写过这份产出的眼睛。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> **执行方式**（按能力降级，**优先用更隔离的方式**）：
>
> 1. **Agent Teams（最优）**：开一个独立的 reviewer agent……让它逐项核查并**严格汇报结论**
> 2. **subAgent（次优）**……
> 3. **自检（兜底）**……不允许目测一遍就放行。
>
> **铁律**：拿到结论后**先按 fail 项把产出改完**，再向用户汇报……

**机制说明:** 两个设计点。第一，检查方式按手头能力一档一档降：有 Teams 用 Teams，没有用 subagent，再没有就自己逐项过——在任何环境里都有的执行，不存在「没有 Teams 就算了」。第二，汇报格式里必须带证据：查出了什么、改了什么。用户扫一眼就知道自检是真做了，还是装样子。
**解法层次:** 流程解法
**可迁移性:** 高
**什么时候用:** 任何产出会直接交人验收的 skill——验收前的质量闭环（查 → 修 → 报）写成显式顺序，并指定隔离等级。
**什么时候太重:** 草稿协作场景（用户就要半成品来讨论方向）——先修复再汇报会把讨论的时机改没了。
**反例:** 「输出前请自我检查」不是这招——没有清单出处、没有隔离要求、没有「先修后报」的顺序，三个要件一个不少才是。
**在哪几个 skill 里见过:** web-video-presentation（script / outline / 每章三处复用同一协议）；nuwa-skill 的外部验收同构。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 交付级产出 | 管用 | 用户看到的永远是修复后的版本 |
| 高频小迭代（改一行文案） | 用力过了 | 每次都开 reviewer agent，开销比产出贵 |
| 方向探索期 | 反而碍事 | 用户要的是快速看到想法，不是完美成品 |

**一起读:**
- A4 去 AI 味三层自检（搭配用：A4 是清单内容，A10 是清单的执行协议）
- A11 每章重读指引：抗上下文遗忘（搭配用：一个管「记得规则」，一个管「按规则收尾」）

### A11 每章重读指引：抗上下文遗忘 · 维度：行为

**症状:** 第 1 章做得很好。第 5 章开始又出现三屏纯文字——CHAPTER-CRAFT 的原则没变，变的是它在上下文里的位置：被 4 章代码顶到了视野之外。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 开工时读一遍全部 references，后面凭记忆 | 一张「阶段 × 必读文件」表，Phase 2.4 那行明写「×N 次，每次都看」：CHAPTER-CRAFT.md＋theme.json＋本章 outline 段落＋article 本章段落 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 长会话里「读过」会过期——把「每次开工重读什么」写成显式表格钉进流程，而不是指望 agent 第 7 次还记得第 1 次读过的东西。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> 不同阶段读不同的文件。**长会话里 agent 容易遗忘原则**，特别是 Phase 2.4 的"实现单章"会重复 N 次 —— 每次都要回看核心约束。

配套的收敛动作：「写章节时只读一份 CHAPTER-CRAFT.md」——所有单章规则并进一个文件，重读成本被刻意压低。

**机制说明:** 两个动作配套才有效：先把散在各处的规则合并成一份单一入口的文件，重读才便宜；再把「每次开工必须重读」写成义务，保证真的去读。只做前一半，文件再好也会被忘掉；只做后一半，每次要读八个文件，太贵，没人执行。
**解法层次:** 流程解法
**可迁移性:** 高
**什么时候用:** 同类子任务重复 N 次的 skill（多章写作、多文件重构、批量出图）——给重复站点配「每次必读」清单，并把清单收敛到单文件。
**什么时候太重:** 子任务只重复两三次、规则又短——直接内联在任务描述里更便宜。
**反例:** 「把规则写进 system prompt」不是这招——system prompt 也会被长上下文稀释；要点是每次开工时的主动重读动作。
**在哪几个 skill 里见过:** web-video-presentation；各类「循环体内强制 re-read」的长流程 skill。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| ×N 次的重复生产站点 | 管用 | 第 N 次和第 1 次拿到同样新鲜的规则 |
| 一次性任务 | 没必要 | 没有遗忘窗口 |
| 上下文管理很强的宿主（自动摘要保留规则） | 可以松点 | 遗忘问题被平台部分解决，但重读仍是更稳的下界 |

**一起读:**
- A10 自检协议：先修复再汇报（搭配用：重读保证开工时记得规则，自检保证收工时核对规则）
- A7 第 1 章风格锚点＋硬验收（搭配用：锚点章代码是另一份「不会过期的参考」）

### A12 双源原则＋信息池 · 维度：领域-认知

**症状:** 章节画面只用了口播稿的内容——屏幕等于把口播打了一遍字幕。口播说「有一个工具救了我的结尾」，画面上也只有这行字，没有是哪个工具、改了几处、原文怎么说。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 画面文案 = narrations 文本的视觉化排版 | 口播念「救了结尾」，画面同时挂着原文细节：「Cursor · 改写 7 篇 · 2 篇返工」＋原文 pull-quote——画面信息密度 > 口播信息密度 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 音和画是两个带宽不同的通道：节奏跟口播（为念优化），细节回原文抽（为看优化）——一份素材两次消费。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> **节奏 / 顺序 / 节拍切分** 跟 **`script.md` 口播稿** —— **关键顺序不能乱**。
> **画面细节 / 数据 / 引用 / 案例** 回 **`article.md` 原文章**抽。
>
> **如果你只用了口播稿的内容做章节** —— 屏幕等于把口播打字打了一遍 —— 那就是 PPT，不是视频。

落地件是 outline 每章首段的信息池，每条强制带来源（`—— 来源 article §X / Lxx`），「没标注 chapter agent 回不到原文」。

**机制说明:** 为了能念，口播把精确数字和引用原话都换成了大白话——这些细节没有消失，它们从画面那条路回来了。信息池就是这件事的落地件：不是劝你「记得回去翻原文」，而是提前把细节抽好、每条标着出处，用的时候伸手就拿。
**解法层次:** 表征解法
**可迁移性:** 高
**什么时候用:** 产物有两个并行呈现通道（音＋画、正文＋图表、摘要＋附录）时——别让两个通道复读同一份低密度内容，让窄通道定节奏、宽通道加密度。
**什么时候太重:** 用户只给了口播稿没有原文——skill 自己也降级（信息池退化为「画面装饰元素池」），双源变单源加修饰。
**反例:** 「画面加点装饰图标」不是这招——加的必须是信息（数字、引用、出处），不是视觉噪音。
**在哪几个 skill 里见过:** web-video-presentation；数据报告类 skill 的「图表密度 > 正文密度」同构。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 文章转视频 / 转演示 | 管用 | 原文细节有处可去，画面不再是字幕 |
| 用户直接给口播稿 | 得让一步 | 没有第二个源，密度只能主动设计 |
| 原文本身很薄（500 字随笔） | 看情况 | 池子抽不出三条，硬凑不如坦然单源 |

**一起读:**
- A3 信息保留度 ≥ 60% 硬下限（前置：A3 保住口播通道的密度下限，A12 再往画面通道加码）
- A5 1 项 = 1 step：逐个揭示（搭配用：独占整屏的 step 才装得下信息池的细节）

### A13 AutoStartGate：把绕不开的手势做成仪式 · 维度：平台

**症状:** `?auto=1` 打开页面，预期整片自动播——实际一片寂静：浏览器的 autoplay 政策拦掉了没有用户手势的音频播放，录屏开局就是死机现场。源码注释明写 browsers require a user gesture before audio can autoplay。（证据：作者证词）

**最小对照:**

| 没有这个机制 | 有这个机制 |
| --- | --- |
| 页面加载直接 `audio.play()`——被浏览器静默拒绝，或弹出权限气泡进了录屏画面 | 一张全屏蒙层「Press SPACE to start」：按一次 Space 解锁手势，蒙层消失，之后整片自由——录屏从 Space 后裁起 |

❖ &nbsp; ❖ &nbsp; ❖

**Therefore:** 平台规则绕不开时，把那一次绕不开的人工动作设计成流程的显式仪式，而不是在流程各处打补丁。

❖ &nbsp; ❖ &nbsp; ❖

**机制原文:**

> `autoStarted` exists separately because browsers require a user gesture before audio can autoplay — `AutoStartGate` flips it on space-press.

录制流程把这一下编进了正字法：「按一次 Space → 蒙层消失 → step 0 出现……停止录制 → 后期裁掉头尾（Space 那一下……）就是成品。」

**机制说明:** 蒙层把「平台限制」翻译成了「开拍打板」：用户知道按这一下是流程的一部分，不会以为页面坏了。代码上也干净——autoStarted 单独一个状态，跟模式切换互不掺和，整块补丁锁在一个组件里。
**解法层次:** 脚本解法
**可迁移性:** 低
**不可迁移原因:** 平台伤疤——整张卡都是给浏览器 autoplay 政策擦屁股；政策若变，机制即废。「把绕不开的动作做成仪式」的姿态值得记，但宿主换成无此限制的环境（Electron、原生播放器），这张卡整体作废。

**力度对比:**

| 场景 | 效果 | 为什么 |
| --- | --- | --- |
| 浏览器内自动播放音频 | 管用 | 这是政策的标准解法 |
| Electron / 本地播放器宿主 | 用不上 | 没有 autoplay 限制 |
| 纯视觉自动播（无音频） | 没必要 | 不触发政策，蒙层是多余的一步 |

**一起读:**
- A9 删掉 minHoldMs：动画 ≤ 口播（搭配用：同属 Auto 模式的可预测性工程，一个管时钟一个管启动）

## 残渣与砍掉候选

### CHAPTER-CRAFT.md 的「Part 0~8」幽灵引用

**判定:** 货物崇拜
**理由:** SKILL.md、OUTLINE-FORMAT.md、EXAMPLES/README.md 至少 10 处引用 CHAPTER-CRAFT.md 的「Part 0 十条原则 / Part 1 开工 5 问 / Part 2 决策树 / Part 3 视觉工具箱 / Part 4 时长 / Part 8 反馈速查」——但出厂的 CHAPTER-CRAFT.md（225 行）里没有任何 Part 标题，五问、决策树、工具箱、速查表也都不存在（实测逐文件比对）。这是一次大瘦身后没还完的引用债：agent 按图索骥会扑空，按死链找「开工 5 问」只能自行脑补。砍法：要么补回 Part 结构，要么把所有引用改成现存小节名。

### README 的过期画像

**判定:** 货物崇拜
**理由:** README.zh-CN.md 引用的 `PRINCIPLES.md`、`PATTERNS.md` 文件不存在；工作流图还是旧版的两个 checkpoint（A1 / A2），与 SKILL.md 现行的「一次对齐五件事」冲突（实测）。README 是门面，门面讲旧故事，新用户第一眼就被带偏。

### 出厂示例的 masthead 页眉

**判定:** 过度设计
**理由:** CHAPTER-CRAFT.md 两处红线禁页眉页脚（「舞台无 chrome：没有 header / footer」「禁止出现任何形式的页眉页脚」），但模板自带的 Example.tsx 每个 step 都渲染 `masthead` 页眉，THEMES.md 还要求测试它「读起来像编辑 chrome，不像 navbar」（实测）。出厂示例违反出厂自检——agent 拿示例当参照时，两份规范打架，赢的多半是看得见的代码而不是看不见的清单。

### scaffold.sh 的绝对路径坑

**判定:** 平台伤疤
**理由:** 实测：create-vite@9 把绝对路径目标当相对路径（`/tmp/wvp-slice` 建到了 `./tmp/wvp-slice`），脚本在 `cd` 处中断且报错难懂。文档示例恰好全用相对路径所以主路径未爆，但这是颗上游升级埋的雷——加一行路径归一化或版本钉死就能拆掉。

### `.cursor/skills/...` 硬编码调用路径

**判定:** 平台伤疤
**理由:** SKILL.md 和 THEMES.md 的命令示例全部写死 `.cursor/skills/web-video-presentation/...`，而 manifest 声明兼容 6 种宿主（claude-code、codex-cli 等）——换一个宿主，照抄命令必然 path not found。应改成「skill 包根目录」的相对表述。

## 盲区

- **最关键的不变式没有机器校验：** `narrations.length === 章节代码最大 step + 1` 是整个真相源设计的命门，但 tsc 查不出、extract-narrations 只验证「数组存在」——漏写一个 if 分支就是一个黑屏 step，只能靠人眼点出来。给 extract 加一个「扫 tsx 里 step === N 的最大值并比对」的检查，成本一个下午。
- **token 红线靠肉眼执法：** 「禁硬编码 hex / 字体名」在完工自检里是一条人工勾选项，一行 `grep -E '#[0-9a-f]{3,6}' src/chapters/` 就能机器化，skill 没给。
- **一镜到底对长视频脆弱：** 20 分钟的片子录到 18 分钟时口播错一个字，代价是整片重录。RECORDING.md 没有分章录制＋拼接的 B 方案。
- **信息保留度只有「量」的机器验法：** 字符比例可以 `wc -m`，但「关键事实逐项对得上」的语义半边没有任何工具支撑，全靠 agent 自觉逐项对照。
- **不防垃圾输入：** article 本身事实有错、结构混乱时，skill 的所有机制都在忠实放大它——双源原则会把错误的数字端端正正挂上画面。
