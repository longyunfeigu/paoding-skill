## 产物卡

### article.md

**谁写它:** 用户给原文时由 stage-01 落盘（用户给的就是它，agent 只负责存下来）
**谁读它:** stage-01 写 outline 信息池时抽；每章实现时回读本章对应段落
**它管什么:** 画面信息密度的弹药库——具体数字、引用原话、案例维度、出处时间
**它不管什么:** 节奏。视频讲什么顺序、在哪停顿，它说了不算
**为什么长这样:** 直觉做法是「文章转完口播稿就用完了，删掉」。skill 反着来：article.md 全程保留，因为口播稿是为「念」优化的——为了能念，细节被换成了感受（「翻车了两篇」）；可画面不受念的约束，挂得下精确值（「改写 7 篇 · 2 篇要返工」）。删了原文，画面就只剩口播的字幕，那是 PPT。
**写错会坏什么:** 原文被删或被「精炼版」覆盖后，章节实现只能从口播稿找素材，画面信息密度 ≤ 口播密度，成片变成「带动画的朗读」。

### script.md

**谁写它:** stage-01，按 SCRIPT-STYLE.md 从 article.md 转写
**谁读它:** outline 切章切步；每章 narrations.ts 逐节拍取文本；用户在 Checkpoint Plan 直接改它
**它管什么:** 节拍与顺序——`---` 切开的每一段就是一次点击、一屏画面；还有语气（B 站风、敢说、无 AI 腔）
**它不管什么:** 画面长什么样。它只决定「这一拍讲什么」，不决定「这一拍演什么」
**为什么长这样:** 直觉形态是「视频文案」——一篇更短的文章。skill 把它定义成「能念出口的稿子」并加了两道反直觉的闸：字符数下限（≥ 原文 60%，防摘要化）和张嘴念测试（防 AI 腔）。`---` 分隔符看着是排版，其实是结构：它是后面所有 step 划分的源头。
**写错会坏什么:** 保留度塌了，后面每一站都在放大一份残缺的内容；`---` 切得太粗，单 step 口播超 15 秒，音频校验报警、观众走神。

一个节拍的实际形状（模拟样本）：

```markdown
结果有一个工具，把我写崩了的结尾救回来了。

---

也有一个，把我最得意的开头改没了。
```

### outline.md

**谁写它:** stage-01，和 script.md 同一次思考里产出
**谁读它:** 用户在 Checkpoint Plan 审；每章实现时读本章段落＋信息池；素材清单被 Checkpoint Plan 的第 4 件事消费
**它管什么:** 章节切分、每章 step 数与估时、每步屏幕内容（一行）、章节级信息池、末尾素材清单
**它不管什么:** 动画类型、CSS 手段、时长数值——OUTLINE-FORMAT.md 用一张「必须写 / 不要写」表把这些明文禁掉
**为什么长这样:** 直觉的「开发计划」会把每步的视觉都规划好——越细越显得专业。skill 判定这是陷阱：计划写死动画，章节实现就成了翻译机，全片一种入场动画。所以 outline 故意留白，只锁「内容和节奏」这种改起来贵的决策，把「视觉」这种需要看着内容现场判断的决策推迟到单章实现。信息池是这张表里唯一的「加项」：每条必须带 `—— 来源 article §X` 标注，否则章节实现回不到原文。
**写错会坏什么:** 写了动画 → 全片模板感；信息池没带来源 → 章节实现找不到细节出处，要么放弃挂细节要么编一个；step 估时和总时长对不上（自检要求误差 < 10%）→ 节奏规划失真。

!steal(章节切分经验法则 ｜ 直接抄走 ｜ 任何视频、课程、演示的结构规划)

> outline 规范里这组数字你规划任何内容结构都能直接用：每章 3~8 步（少于 3 太薄，多于 8 观众忘了这章在讲啥）；一章 30~60 秒讲完一个聚焦主题，总时长 ÷ 30 秒 ≈ 章节数；中文口播按 4 字/秒估时（一分钟 ≈ 250 字）；章节边界找「讲者会换语气的位置」——你读稿子时哪里下意识想咳一声接下一段，哪里就该切。

### narrations.ts（×N 章）

**谁写它:** 每章实现时与 Chapter.tsx 同目录创建
**谁读它:** useStepper 拿数组长度当 step 数；extract-narrations.ts 拿元素当音频文本；Auto 模式按 index 找对应 mp3
**它管什么:** 这一章有几步、每步念什么——step 数和口播文本的唯一真相源
**它不管什么:** 画面。它和 Chapter.tsx 是同目录的两个文件：一个管说，一个管演
**为什么长这样:** 直觉做法是章节组件里写个 `totalSteps = 9`，音频流水线再从 outline 或 script 里取文本——于是 step 数存在两处、文本存在三处，谁改了一处其它就成了谎言。skill 把这两个信息压进同一个数组：长度即 step 数，元素即文本，其它地方连存这个数的字段都没有（chapters.ts 注释原话：there is no `totalSteps` to maintain separately）。「想漂移，没有地方可写」是比「写校验脚本对账」更深一层的解法。
**写错会坏什么:** 数组长度 < 章节代码的最大 step＋1 → Auto 模式提前翻页，最后几屏永远播不到；文本和 script.md 语义漂了 → 录屏画外音和字幕对不上，观众听出「稿子不是同一份」。

真实标本（来源：切片实测，工程自带示例章）：

```ts
export const narrations: Narration[] = [
  // step 0 — magazine cover
  "这是示例章节的第一步。把这一行换成你这一步的口播文案。",
  // step 1 — split layout
  "第二步。每个数组元素对应章节里 step === N 的那一屏。长度必须严格相等。",
  // step 2 — pull-quote close
  "第三步。这个数组就是音频合成 + 自动播放的唯一真相源——再也不会和章节代码漂移。",
];
```

逐字段看设计：数组**长度**（3）就是这章的 step 数，useStepper 直接 `narrations.length`，写错一个少播一屏；**元素文本**会被逐字送进 TTS，所以标点断句按「念」优化（语义必须与 script.md 一致，这条靠完工自检的人工对照）；**空串** `""` 是合法值，意思是「这步静音」——extract 跳过它不烧 TTS，运行时按字数估时撑过去；**注释**里的 step 编号是给人看的，机器只认 index。

### Chapter.tsx ＋ Chapter.css（×N 章）

**谁写它:** 每章实现（主线程或 subagent）
**谁读它:** 运行时渲染；后续章节拿第 1 章的当代码风格参考
**它管什么:** 这一章每个 step 的整屏画面：`if (step === N) return <FullScene />`
**它不管什么:** 推进逻辑（全局 stepper 管）、配色字体（token 管）、别的章（物理隔离，禁止跨章 import）
**为什么长这样:** 章节是 step 的纯函数，没有定时器没有内部状态——直觉的「动画序列」做法（setTimeout 串场）在录屏场景是灾难：录到一半重来一次，状态对不上。纯函数让任何 step 可以随时跳达、重放、倒带。每章独立 CSS 前缀（`.cd-` / `.sd-`）不是代码洁癖，是并行开发的前提：subagent 互相看不见，唯一的安全策略是物理上碰不到对方的文件。
**写错会坏什么:** 用了 setTimeout → Auto 模式音频时钟和动画时钟打架；硬编码 `#ff4a2b` → 换主题那一章瞬间违和（THEMES.md 判词：bug 在章节里，不在主题里）。

### tokens.css ＋ .theme

**谁写它:** scaffold.sh 从 `themes/<id>/tokens.css` 物理拷贝；`.theme` 存主题 id 一行
**谁读它:** 所有章节 CSS 通过 `var(--accent)` 等语义 token 消费；`.theme` 给人查「这工程从哪个主题起步」
**它管什么:** 调色板（4 表面色＋4 文字色＋3 accent）、四个字体家族、性格旋钮（圆角、分割线、hero 数字风格、舞台 padding）、装饰层
**它不管什么:** 字号、间距、动画时长——这些明文划给章节自由发挥
**为什么长这样:** 直觉做法是把主题做成运行时配置（theme switcher、context、条件分支）。skill 选了最笨的方案：构建期拷一个文件。代价是不能动态切换，换来的是章节代码完全主题无关——验证「换主题不破」只需要覆盖一个文件刷新一下。token 边界画在「颜色＋字体必须、其它自由」也是刻意的：管太宽（间距时长全 token 化）章节就没了创作空间，管太窄（只管色值）换主题字体就破。
**写错会坏什么:** token 命名层级用错（拿 `--text` 当装饰色）→ 换到浅色主题对比度塌掉；章节绕过 token → 主题切换的承诺作废。

真实标本（来源：切片实测，midnight-press 节选）：

```css
:root {
  --shell:   #0d0b09;   /* letterbox 外圈，比舞台更深 */
  --surface: #1a1714;   /* 舞台主底——暖 espresso，不是纯黑 */
  --accent:  #ff4a2b;   /* 唯一的饱和色 */
  --font-display-cn: "Noto Serif SC", "Source Han Serif SC", serif;
  --dur-cinematic: 1600ms;  /* 主题的慢节奏签名 */
}
```

`--shell` 比 `--surface` 更深是 THEMES.md 的明文规则（「这样舞台读起来是主体，外围会退后」）；`--accent` 全主题只许一个饱和色——第二个饱和色会和第一个打架。

### chapters.ts

**谁写它:** 每章完成后注册一行（import 组件＋import narrations＋数组里加一项）
**谁读它:** useStepper 算全局游标和章节偏移；extract-narrations.ts 用正则读章节顺序
**它管什么:** 章节的顺序——数组顺序就是放映顺序
**它不管什么:** step 数（直接引用各章 narrations，不另存数字）
**为什么长这样:** 注册表是并行开发里唯一的「共享写入点」，所以模式 C 的硬规则是 subagent 不许碰它——全部注册动作收回主线程做。它故意瘦：每章只有 id、title、narrations、Component 四个字段，没有任何会和章内信息重复的字段。
**写错会坏什么:** 顺序排错 → 放映顺序错；id 和文件夹名对不上 → extract 直接报错（实测错误文案：chapter id "X" registered but no matching folder found）。

### audio-segments.json

**谁写它:** `npm run extract-narrations`（机器产物，禁止手编）
**谁读它:** 用户在合成前扫一眼；synthesize-audio.sh 逐条消费
**它管什么:** 「即将花钱合成的文本」的扁平清单：章节、step、文本、目标路径
**它不管什么:** 怎么合成（音色、并发、重试是 synthesize 脚本的事）
**为什么长这样:** 它本可以不存在——synthesize 直接扫 narrations.ts 也能跑。专门落一个 JSON 是为了在「烧钱」前插一个人审点：用户扫一遍文本，错字、漏拍、切分问题在这里抓住，比合成完听出来便宜得多。step 用 1-indexed 是为了和音频文件名 `1.mp3` 对齐，少一次心算。
**写错会坏什么:** 它是构建产物，手编它等于把真相源改回多处——下次 extract 一跑全部覆盖。

真实标本（来源：切片实测）：

```json
{
  "chapter": "example",
  "step": 1,
  "text": "这是示例章节的第一步。把这一行换成你这一步的口播文案。",
  "audio": "example/1.mp3"
}
```

`chapter` 是章节 id（也是音频子目录名）；`step` 从 1 数（对齐文件名，narrations 数组里它是 index 0）；`text` 就是要送进 TTS 的原文；`audio` 是合成脚本的落盘目标，运行时 useAudioPlayer 按同样的约定拼路径——两边从不通信，靠命名约定相遇。

### public/audio/&lt;id&gt;/&lt;N&gt;.mp3

**谁写它:** synthesize-audio.sh 调 mmx 串行生成
**谁读它:** useAudioPlayer 在 audio / auto 模式按 `audio/<章节id>/<step+1>.mp3` 拼路径播放
**它管什么:** 每个 step 的画外音，以及 Auto 模式的推进时钟（播完＋200ms → next）
**它不管什么:** 找不到它时的兜底——404 时运行时按字数估时（`max(1500ms, 字数 × 250ms)`）继续推进，预览不中断
**为什么长这样:** 一个 step 一个文件而不是整章一条音轨，是为了让「改一步」便宜：重写第 14 步的口播，只重合成 14.mp3，其余 37 个文件不动（合成脚本天然增量：已存在跳过）。
**写错会坏什么:** 文件名和 step 错位 → 张冠李戴地配音；单段超长（≥15s）→ 校验报警，说明上游 step 没拆够。

### localStorage 游标（STORAGE_KEY）

**谁写它:** useStepper 每次推进时持久化 `{chapter, step}`
**谁读它:** 下次打开页面恢复进度
**它管什么:** 开发期的便利——改完代码刷新，不用从第 1 章点回来
**它不管什么:** 结构变更的安全。章节增删或 step 数变化后，旧游标可能指向不存在的位置
**为什么长这样:** 这是唯一一个「方便带来风险」的产物，所以配了双保险：规程层要求大改后 bump STORAGE_KEY 版本号（v4 → v5，旧键整体作废）；代码层 sanitize 函数把任何越界游标钳回合法范围。两层防同一件事，因为前者靠人记得、后者兜人忘了的底。
**写错会坏什么:** 两层都失效时，打开页面落在已删除的 step 上——这正是作者证词里「老问题」的一种。
